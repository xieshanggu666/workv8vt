# 📡 舆舟 · 全网舆情监测与危机管理平台

基于 **Vue 3 + Vite + Pinia（前端）+ Express + SQLite（后端）** 的舆情监测与危机处置演示平台。所有数据为 mock，模拟舆情采集与处置闭环。

## 技术栈

- 前端：Vue 3 + Vite + Pinia
- 后端：Node 内置 `node:sqlite` + Express，REST API
- 数据库：`server/pubmon.db`（SQLite，首次启动自动建表 + 预置示例舆情）

## 运行

```bash
npm install
npm run dev
```

前端 http://localhost:5200（Vite 已代理 `/api` 到 http://localhost:4130）。需 Node ≥ 22.13。

## 功能

- **舆情总览**：总量/正面/中性/负面/热点/负面占比统计、未解除预警与在办危机闭环统计、情感分布环形图、7 时段热度趋势、渠道来源分布、高频热词云、生效预警规则、危机速览
- **舆情列表**：按情感/渠道/关键词筛选，录入新舆情自动进行情感分析，负面舆情触发预警提示；支持可恢复批量导入（任务化、断点续跑、失败重试、进度与逐条结果回写）
- **数据源采集**：管理员配置多源连接（API/RSS/爬虫），值班员启停采集任务；游标落库断点续采、失败退避重试与故障自动停止、幂等键去重；新舆情自动进入情感→预警→危机→通知闭环
- **预警中心**：预警规则配置与**编辑**（级别/关键词/情感/热度下限/归并话题/时间窗口），规则启停、触发记录与关联舆情、单条/批量解除预警（**幂等**，重复解除不产生重复时间线）
- **危机处置**：事件建档（话题+方案+研判+邮箱）、状态流转（监测→处置→结案）、处置时间线、动作记录、事件回溯（按规则拆分统计、统一结案守卫检查清单、结案档案含守卫快照）与结案总结；**统一结案守卫**（工单/声明/外部协作/复盘报告全部闭环）通过后，级联解除预警、联动中止在途通知并冻结结案档案，**结案可回滚并精确恢复预警与通知任务**
- **协同工单**：从危机**拆分跨角色工单**（公关/法务/运营/客服/协调组），指派/认领、状态流转（待分派→处理中→已完成，可阻塞/取消/回退打回重做）、**SLA 两级超时升级**（阻塞挂起计时、恢复顺延）；完成结果**回写危机时间线并可联动解除预警**，联动通知调度与权限控制，**未完结工单阻塞危机结案**
- **舆情传播路径分析**：沉淀话题的**来源、传播节点、转发关系与影响阶段**（潜伏期→发酵期→爆发期，可标记回落/二次爆发），节点/KOL/热度/触达/传播层级实时聚合；**关联预警规则与危机事件**（按话题/规则自动挂接），按传播变化（爆发升级/热度激增/KOL 加入）**触发通知**，爆发期可**自动生成跨角色处置工单**，全程变化留痕并回写危机统一时间线
- **通知中心**：多渠道订阅与通知编排——按预警规则/话题/危机状态/**协同工单事件（拆分分派/改派/认领/超时升级）/传播路径事件（爆发升级/异动激增·KOL）/外部协作事件（提交到达/紧急升级）/危机声明渠道事件（单渠道失败/部分渠道失败督办）**生成**可暂停**的通知任务，调度器自动发送、失败退避重试、回执超时自动升级；同一分派/升级的多渠道任务以 `corr_id`+`seq` 串联为可追踪链路（声明类任务为 `stmt{id}:channels/partial`），全部动作镜像关联工单日志并实时聚合为工单链路状态；确认回执**同步解除关联预警并写入带工单/声明锚点的危机时间线**；覆盖渠道与订阅配置、调度、角色权限与全程历史追踪
- **危机复盘报告**：汇总**预警、处置时间线、传播路径、协同工单、危机声明、通知回执、结案档案**同源快照，支持**跨角色分段编制**（六章节各自记录最后编辑人）→ 提交审核 → 审核发布（驳回可重编）；每次送审/发布/回滚均**归档不可变版本**，支持**版本对比与一键回滚重编**；审核通过自动**回写有效结案档案与统计口径**（已回滚的历史档案保留结案时点版本口径；新结案时重新冻结当次发布版本）
- **危机声明**：公关**起草危机声明**（标题/正文/优先级/拟发布渠道，可关联处置工单）→ 提交**法务审核**（通过/驳回，驳回退回起草可修改重送）→ 审核通过后**发起分渠道发布**（官方微博/微信公众号/官网/新闻通稿/短视频/新闻发布会），发布人员**分渠道执行并逐条登记结果**（执行中/已发布+回执链接/失败原因，失败可重试、可放弃单渠道）；起草/送审/审核/每个渠道进度**实时回写处置工单日志与危机统一时间线**；**全部渠道成功才自动置已发布，存在失败渠道时置「部分渠道失败」（发布未完成），即时生成渠道失败提醒与需回执的部分失败督办通知（复用失败重试/回执超时升级）并阻断危机结案**，失败渠道重试成功或放弃（取消）后才能完成；**未完结声明阻塞危机结案**
- **外部协作反馈门户**：**品牌方 / 监管方 / 媒体**通过独立外部门户（凭专属口令 `x-access-code`）提交**证据材料 / 整改进度 / 线索**（可挂接未结案危机、登记附件清单、标记紧急、留来源链接）；内部值班员**受理**、管理员**审核采纳/驳回**——采纳后事务化**回写协同工单日志**（`work_order_logs.action='ext'`）、可勾选**联动解除该危机全部未解除预警**（`resolve_kind=portal`，状态守卫幂等）并写入**危机统一时间线**（`ref_type='ext'` 锚点，看板可点击直达）；紧急提交（如监管督办）**提交即联动通知升级**（新增 `ext_event=submitted/escalated` 订阅，复用失败重试/回执超时升级）；外部门户与内部数据隔离（仅见本人提交、可见驳回原因、可补充材料/采纳前撤回），复盘报告聚合快照新增「外部协作反馈」章节

## 危机声明（起草 → 法务审核 → 分渠道发布登记）

- **公关起草**：为任一未结案危机起草声明（`crisis_statements`），填写标题、正文、优先级（紧急/高/普通）与拟发布渠道（官方微博/微信公众号/官网新闻中心/新闻通稿/官方短视频/新闻发布会），可选**关联处置工单**（`work_order_id`，须属于同一危机且未取消）；起草即写危机时间线「声明起草」与工单日志
- **法务审核状态机**：`draft 起草中 → review 待法务审核 → approved 审核通过`；驳回退回起草（`draft`，带驳回意见红条提示），修改后可再次送审，每次送审/通过/驳回均写留痕；审核通过/驳回**回写危机时间线与处置工单日志**（标注法务审核人）
- **分渠道发布执行与登记**：审核通过后发起人一键发起，`approved → publishing`，按渠道清单落 `crisis_statement_channels` 执行行（路径内幂等）；发布人员**逐渠道登记**：执行中 `publishing` / 已发布 `success`（必填回执说明、可填发布链接）/ 失败 `failed`（必填失败原因）；失败渠道可**重试**（重置待执行）、待执行/执行中渠道可**取消**
- **进度回写与自动完成**：每一次渠道登记都写危机统一时间线「声明渠道」并**回写处置工单日志**（`work_order_logs.action=stmt`，工单卡片显示关联声明徽标）；全部渠道到达终态时按结果收口：**全部成功（或成功+放弃取消、无失败）→ `published` 已发布；存在失败渠道 → `partial` 部分渠道失败（发布未完成，写「声明部分失败」时间线、触发通知升级、阻塞结案）；全部渠道取消且无任何成功/失败 → `cancelled`**。失败渠道**重试**（声明重回 `publishing`）后成功即发布完成；也可在 partial 状态下**放弃（取消）失败渠道**，无剩余失败时收口为已发布
- **可配置降级发布**：分渠道失败处理由「一律部分失败、阻断结案」升级为可配置的降级发布，策略三档——**`block` 阻断**（原口径，必须重试成功/逐渠道放弃）、**`manual` 手动确认降级**（默认；partial 且满足门槛时发布人员确认后降级收口）、**`auto` 自动降级**（全部渠道登记完且满足门槛时系统自动收口）；门槛为「最大失败渠道占比（默认 ≤50%）+ 至少成功渠道数（默认 1 个）」。策略存 `app_config`（管理员在声明看板全局配置），单份声明可在起草/编辑/发起发布/partial 阶段单独覆盖（`crisis_statements.degrade_policy`，空=沿用全局默认，可重置）。降级后声明进入新终态 **`degraded` 已降级发布**：与逐渠道放弃不同，失败渠道**保留 failed 失败记录**（审计可溯）但随声明终止，**不再阻塞危机结案**；失败渠道事后仍可重试，全部成功后自动恢复 `published`（留痕 `degrade_recovered`，降级标记清除、过程日志保留）。`degraded/published` 为已对外发布终态不可取消
- **降级联动通知**：新增声明通知订阅维度 `stmt_event='degraded'`（降级发布知会，手动/自动均触达），幂等键 `stmt:{声明id}:degraded:sub{订阅}:ch{渠道}` 内 idem 标签 `degraded:{降级轮次}`、`corr_id=stmt{id}:degrade`；补齐恢复后再次降级可再次知会。原 `chfail`（单渠道失败即时提醒）/`partial`（部分失败督办、建议需回执）文案同步纳入降级选项
- **结案守卫与复盘快照**：`degraded` 与 `published` 同为发布终态，**不计入**未完结声明（`crisisOpenStatementCount`/守卫四项检查/看板失败渠道计数仅统计 `partial` 声明下仍失败的渠道）；`closureReadiness` 额外返回 `degradedStatements`，结案守卫快照冻结 `statements.degraded` 计数、结案时间线附降级说明。复盘聚合快照 `statements.degraded` 单列计数，降级声明带 `degraded_mode/degraded_by/degraded_at/degrade_reason` 明细
- **历史部分失败兼容**：老库迁移补齐降级策略字段与 `app_config` 表（缺省首次访问时按内置默认 `manual/50%/1` 幂等回填），历史 `partial` 声明**状态与阻断语义保持不变**（不带策略覆盖=完全沿用全局口径，默认 manual 下满足门槛即可手动降级，是对存量记录的兼容升级路径而非自动放行；设全局为 `block` 则与旧行为完全一致）；历史脏数据修复（误置 `published` 的含失败渠道声明重算为 `partial`）保持原逻辑；新订阅「声明降级发布知会」按名称幂等补齐
- **失败通知升级**：复用通知编排，订阅匹配维度 `stmt_event`（`chfail` 单渠道发布失败即时提醒 / `partial` 部分失败督办，建议需回执 / `degraded` 降级发布知会）；任务以 `statement_id` 关联声明、`corr_id=stmt{id}:channels/partial/degrade` 串联，沿用失败退避重试与**回执超时升级**（升级子任务继承声明来源，写带 `ref_type='statement'` 锚点的危机时间线「通知升级」）；幂等键 `stmt:{声明id}:chfail:{渠道行}:a{尝试次数}/partial:{轮次}/degraded:{降级轮次}`，重试后再次失败可重新触达，重启为存量 partial 声明补生成（幂等）
- **取消与结案守卫**：起草/待审/已通过/发布中/**部分失败**均可取消整份声明（在途与失败渠道一并取消）；**已降级发布/已发布不可取消**；危机结案时若存在未完结声明（draft/review/approved/publishing/**partial**）返回 400 拦截，须先完成全部渠道（失败重试成功、放弃或确认降级发布）或取消；已结案事件不能再起草声明。复盘快照「危机声明」章节与结案守卫同口径，partial/degraded 各单列计数
- **发布状态一致性修复（历史库自动迁移）**：旧口径「全部渠道登记完成即已发布」会让含失败渠道的声明被误置 `published` 并放行结案；启动时按渠道实况统一重算（仍有在途渠道→`publishing`、全终态有失败→`partial`、全部取消→`cancelled`）并补迁移留痕，升级链通知任务补齐 `statement_id`、清理来源悬空的声明通知孤儿
- **权限模型**（演示，与其他模块一致）：`viewer` 只读；`ops` 值班员（公关/发布角色）可起草·编辑·送审·发起发布·渠道执行登记·重试·取消；`admin` 管理员同 ops 且独占**法务审核通过/驳回**（可切换身份至法务「陈律」）；越权 403、越态 400
- **复盘衔接**：复盘报告聚合快照新增「危机声明」章节（每份声明的审核状态、法务意见、关联工单、分渠道执行结果）
- 主要接口：`GET /api/statements`（状态/危机过滤 + 看板汇总 + 字典 + 全局降级策略）、`POST /api/statements`、`GET /api/statements/:id`（含分渠道登记与留痕）、`PUT /api/statements/:id`、`POST /api/statements/:id/{submit|approve|reject|publish|cancel|degrade}`、`PUT /api/statements/:id/degrade-policy`（声明级覆盖/重置）、`GET/PUT /api/statements-config/degrade-policy`（全局策略，PUT 仅 admin）、`POST /api/statement-channels/:chId/{register|retry|cancel}`

## 外部协作反馈门户（外部提交 → 内部审核 → 回写闭环 → 通知升级）

- **外部身份与门户**：协作方（`ext_partners`：品牌方 brand / 监管方 regulator / 媒体 media）由管理员登记机构、联系人与专属**提交口令**（`access_code`，可启停；停用后口令立即失效、历史提交保留）。外部请求经 `x-access-code` 头鉴权，与内部 `x-role` 权限模型相互独立；门户首页只返回**本人提交**与未结案危机只读清单，**跨方访问 404、口令无效 401**，数据严格隔离
- **提交内容**：类型 `evidence 证据材料 / rectify 整改进度 / clue 线索反映`，含标题正文、附件清单（`attachments` JSON，演示仅登记文件名/大小/类型不落文件）、来源链接、联系方式、`is_urgent` 紧急标记；可挂接任一**未结案危机**（已结案拦截），也可作为**通用线索**不挂事件，由内部核实后补挂/改挂
- **内部审核状态机**：`pending 待审核 → reviewing 受理中 → accepted 已采纳 / rejected 已驳回`；提交方在采纳前可**补充材料**（追加留痕并回写时间线）或**主动撤回**（`withdrawn`，已采纳为处置档案不可撤）。ops 值班员可**受理**与**补挂危机**；**采纳/驳回仅 admin**（越权 403、越态 400、缺驳回原因 400）；驳回原因外部门户可见，补充后可重新受理、再采纳（采纳/受理自动清除历史驳回标记）
- **采纳回写（事务化）**：① 回写关联协同工单日志 `work_order_logs.action='ext'`（工单须属于同一危机且未完结，否则 400；只挂证据不改工单状态）；② 勾选时**联动解除该危机全部未解除预警**（`alert_events.resolve_kind='portal'`，状态守卫幂等，记录实际解除条数与涉及规则）；③ 写入**危机统一时间线**「外部反馈采纳/提交/升级/补充」（`crisis_timeline.ref_type='ext'` 锚点，危机卡片时间线可点击直达门户详情）；已结案事件不回写，保证结案档案稳定
- **补挂/改挂整体迁移（事务化，防串案）**：仅未采纳（待审核/受理中/已驳回）提交可改挂，**已采纳为处置档案禁止改挂**（工单回写/预警解除已成事实），已撤回不可改挂；改挂时随提交归属**整体迁移**：① 该提交在旧危机时间线的全部 `ref_type='ext'` 锚点行（保留原时间/动作）搬到新危机，旧/新危机各写一条「外部反馈改挂」交接记录（旧危机的交接记录不带锚点，已结案旧危机只搬不写、保持结案档案稳定），解除挂接则锚点行从所挂事件移出、提交转回通用线索；② 关联外部协作通知任务（含回执超时升级链后代，同步回填 `ext_submission_id`）的 `crisis_id` 重新指向新事件/置空并逐条留痕（`notify_logs.action='rebind'`）；启动时 `healSubmissionCrisisLinks` 按同口径幂等修复旧版遗留串案（采纳提交以回写工单危机为权威归属，无工单以采纳锚点所在危机为准）
- **联动通知升级**：复用通知编排，新增订阅匹配维度 `ext_event`（`submitted` 提交到达 / `escalated` 紧急升级，与预警/危机/工单/传播订阅互斥校验）；普通提交按「提交×订阅×渠道」幂等生成提醒任务，**紧急提交（监管督办等）提交即额外生成需回执的升级督办任务**（沿用失败退避重试与回执超时升级）；幂等键 `ext:{提交id}:{事件}:sub{n}:ch{n}`，启动时为存量紧急待办补生成（幂等）
- **全程留痕与跨视图**：`ext_submission_logs` 记录提交/补充/撤回/受理/采纳/驳回/补挂/紧急升级，区分 `operator_side`（external 外部 / internal 内部 / system）；危机卡片「🤝 外部协作」角标（待审数+紧急数+已采纳数）、总览统计卡（待审/紧急）、危机时间线锚点跳转、复盘报告同源快照「外部协作反馈」（按品牌/监管/媒体拆分、采纳/驳回/紧急/联动解除预警计数与逐条结论）
- **删除与归档口径**：删除危机事件时外部提交**保留**（跨主体协作留痕不随事件删除），仅解除危机/工单引用；停用协作方不影响已提交材料

## 跨角色危机协同工单
- **统一调度链路（dispatch chain）**：分派/改派/认领、SLA 超时一级/二级升级、通知发送、失败自动/手动重试、回执确认与回执超时升级共享同一套可追踪状态流——同一次分派/升级的多渠道通知任务共享 `notify_tasks.corr_id`（`wo{id}:dispatch`/`wo{id}:escalate`）并以 `seq` 标识调度轮次（改派、逐级升级递增）；通知侧每一步动作（生成/送达/重试/失败/暂停/回执/升级/取消）实时**镜像进工单日志**（`work_order_logs.notify_task_id`），工单详情「🔗 调度链路」把工单动作与通知留痕按时间归并展示；工单持有聚合后的链路状态 `dispatch_state`（未触发/发送中/发送失败/部分渠道送达/已送达/已回执/已取消）
- **拆分与指派**：从任一未结案危机拆分工单，填写任务说明、类别（公关口径/法务合规/现场运营/客诉跟进/其他）、优先级（紧急/高/普通）、SLA 时限；创建时可直接**指派**处理人（含职能团队），留空则**待分派**供值班员**认领**；首次分派、认领、每次**改派**均作为新调度轮次触发通知（按「轮次×处理人」幂等，`dispatch_seq` 递增）
- **状态机**：待分派 `todo` → 处理中 `doing` → 已完成 `done`；处理中可**阻塞挂起**（`blocked`，SLA 计时暂停），恢复后按阻塞时长**自动顺延截止时间**；已完成可**回退打回重做**（`rework`，保留原结果留痕、可重新指派）；未完成可**取消**。所有流转带状态守卫（越态操作返回 400），全程写入 `work_order_logs`（含操作人与职能团队、链路事件名 `wo_event`）
- **超时升级（两级）**：调度器每 3 秒扫描到期工单——到期即**一级升级**（待分派单催认领、处理中单催处理人），一级升级 60 秒仍未完成则**二级升级督办**（管理员介入）；升级进入同一 `corr_id` 链路（seq=1/2），升级动作写带工单锚点的危机时间线「工单超时/工单升级」
- **结果回写与预警联动**：完成时必填处理结果，回写危机时间线「工单完成」；可勾选**联动解除该危机下全部未解除预警**（`resolve_kind=workorder`，状态守卫幂等）；拆分/分派/改派/认领/阻塞/恢复/回退/取消均回写统一时间线（`crisis_timeline.ref_type='workorder'` 锚点，看板时间线可点击直达工单链路）
- **通知联动与终态收敛**：工单事件复用通知编排——`notify_subs.wo_event`（`created` 拆分/分派/改派/认领、`escalated` 两级超时升级）按「工单×轮次×事件×订阅×渠道」幂等生成通知任务，沿用失败退避重试、回执超时升级（升级子任务继承 `corr_id` 与 `work_order_id`）与回执闭环；**工单完成/取消时自动取消仍在途**（待发送/失败/暂停）的分派与升级通知并重算链路状态，避免完结后继续催办
- **跨视图同口径**：危机卡片「🔗 调度链路」角标、工单看板头部（在途/失败/重试/回执）、总览统计卡与复盘快照的工单/通知统计均由 `server/dispatch.js` 同一聚合函数（`deliveryRollup`/`crisisDispatchSummary`）产出
- **结案守卫**：危机结案时若存在未完结工单（todo/doing/blocked）返回 400 拦截，须先完成或取消全部工单（统一结案守卫四项之一，与未完结声明/待审核外部提交/复盘报告未发布同源校验）；回滚结案不影响既有工单，被中止的工单链路通知随回滚恢复并重算链路状态
- **权限模型**（演示，与其他模块一致）：`viewer` 观察员只读；`ops` 值班员与 `admin` 管理员可拆分/指派/认领/流转/完成/回退/取消；越权返回 403
- 主要接口：`GET /api/work-orders`（状态/危机/处理人过滤 + 看板汇总含通知链路）、`POST /api/work-orders`、`GET /api/work-orders/:id`（操作日志 + `trace` 统一调度链路 + 关联通知任务）、`POST /api/work-orders/:id/{claim|assign|start|block|complete|rework|cancel}`

## 舆情传播路径分析

- **路径沉淀**：一个话题一条传播路径（`prop_paths`），含话题、首发来源舆情、关联危机/来源预警、影响阶段、峰值热度、爆发自动工单开关；建档时可指定首发来源节点与首条来源舆情，未指定危机时按「同话题未结案事件」自动并入（与预警→危机归并同口径）
- **节点与转发关系**：节点（`prop_nodes`）分首发来源 `root` / 媒体 `media` / 头部账号 `kol`（粉丝 ≥100w）/ 普通节点 `node`，同名节点自动合并（路径内幂等）；转发关系（`prop_edges`）记录 from→to、转发/评论/点赞/触达/热度与对应舆情，**幂等键去重**（调用方可传 `idem_key`，否则按「路径+边+分钟桶」生成，重采/重复上报不重复入库）
- **影响阶段自动推进**：转发关系入库后实时聚合（节点数、KOL 数、峰值热度、累计触达/转发、BFS 传播层级），阶段机 `seed 潜伏期 → ferment 发酵期 → outbreak 爆发期`：节点≥3 或热度≥45 进入发酵；节点≥4 且热度≥60、或 KOL（粉丝≥100w）转发且热度≥60 进入爆发；阶段**只升不降**，可人工标记 `decline 回落期`，回落期再次达到爆发阈值可**二次爆发**
- **变化触发通知**：爆发推进触发 `outbreak`（爆发升级）；非爆发场景单跳热度≥60 且较路径峰值激增≥15 触发 `surge`；KOL 转发（未达爆发）触发 `kol` 异动。复用通知编排：订阅按 `prop_event`（outbreak/surge，surge 订阅同时承接 KOL 加入）+ 话题匹配，按「路径×事件×订阅×渠道」幂等生成任务，沿用失败退避重试与回执超时升级；启动时为存量爆发期路径补生成（幂等）
- **关联预警与危机**：路径↔预警规则多对多（`prop_path_alerts`，可标记来源规则）；预警管线触发时按「已关联规则 或 同话题」自动挂接活跃路径并补关联危机；路径↔危机手动/自动关联后，建档/发酵/爆发/回落/工单动作**写入危机统一时间线**（传播建档/传播发酵/传播爆发/传播回落）；危机卡片与预警触发记录可一键跳转路径（按危机过滤）
- **跨角色处置工单**：路径配置 `auto_wo` 开启且关联危机时，**每轮爆发自动拆分一张**紧急公关工单（待分派、SLA 60 分钟，`work_orders.prop_path_id` 标记来源，本轮已生成则幂等跳过）；也可手动从路径拆分任意类别/优先级工单。工单卡片标注「🕸 源自传播路径」，删除路径时来源工单保留（处置留痕）
- **全程留痕与权限**：阶段推进/转发/关联/回落/自动工单/编辑落 `prop_change_logs`（含操作人）；`viewer` 只读、`ops` 可建档/记录转发/关联/阶段操作/拆单、`admin` 同 ops 且可删除路径；停用路径（`archived`）不再推进阶段或触发通知
- 前端「🕸 传播路径」页：阶段筛选与爆发角标、SVG **传播关系图**（BFS 分层、KOL/高热度边高亮、转发箭头）、转发关系明细、记录转发弹窗（已有/新建节点）、关联危机/预警、生成工单、变化留痕；总览页含监测/爆发路径统计卡与传播速览
- 主要接口：`GET /api/prop`（阶段/危机/话题过滤 + 汇总 + 阈值字典）、`GET /api/prop/:id`（含节点/边/留痕/聚合指标）、`POST/PUT/DELETE /api/prop`、`POST /api/prop/:id/crisis`、`POST/DELETE /api/prop/:id/alerts[/:alertId]`、`POST /api/prop/:id/edges`、`POST /api/prop/:id/decline`、`POST /api/prop/:id/work-orders`

## 危机复盘报告

- **数据汇总（同源快照）**：一份危机事件一份复盘报告（`crisis_reports`）。建档即冻结首版聚合快照，编制中可手动「刷新聚合数据」，送审/发布时自动再冻结；快照内容全部 SQL 直查，与各业务模块同口径：
  - **预警**：触发总数/未解除/已解除、按规则拆分（含级别与待处置数）、逐条触发记录（关联舆情、解除途径 manual/batch/close/notify/workorder）
  - **处置时间线**：危机统一时间线全量（建档/预警解除/工单/传播/结案/回滚等所有动作）
  - **传播路径**：关联路径条数与爆发数，每条含阶段、节点/KOL/转发关系数、累计触达、峰值热度
  - **协同工单**：状态分布（待分派/处理中/阻塞/完成/取消）、超时/两级升级数、逐条处理人、通知链路（渠道送达/回执/在途/失败/重试/回执升级）与完成结果留痕——与工单看板同一聚合口径
  - **通知回执**：任务状态分布、已回执/回执超时升级/失败/**自动重试次数**计数（计数不受明细窗口限制）、逐条渠道、尝试次数、关联工单与链路轮次、回执确认人/意见——与危机卡片「调度链路」角标同一数据源
  - **结案档案**：历次结案/回滚记录及其回写的报告版本
- **跨角色分段编制**：报告分六个章节（事件概述、原因分析、处置时间线复盘、响应与传播评估、经验教训与改进措施、附录），任一值班员/管理员可独立编写任一章，**每章记录最后编辑人与编辑时间**，支持公关/法务/运营/客服等职能团队在同一份报告上协作
- **审核状态机**：`draft 编制中 → reviewing 待审核 → published 已发布`；编制中可随时保存章节/刷新快照；提交审核自动冻结快照并归档送审版本，审核中章节锁定不可编辑；管理员可**审核通过并发布**（归档发布版本）或**驳回**（退回编制中，送审版本保留留痕）
- **版本归档与回滚**：提交审核、审核发布、版本回滚均生成**不可变版本快照**（`crisis_report_versions`，含章节内容与聚合数据双快照）；版本面板可逐章展开并高亮「与当前内容有差异」；管理员可**一键回滚到任意历史版本**——以该版本内容覆盖当前工作区、报告退回编制中，并再归档一个 `rollback` 版本（记录来源版本），版本链完整可溯、永不丢历史
- **回写结案档案与统计口径**：结案时由结案链路冻结当次已发布报告（id/版本/标题写入 `crisis_closures.report_id/report_version/report_title`）；历史先结案后发布的场景，审核通过时回写最近一次**有效（未回滚）且未回写**的结案档案，已回滚的历史档案保留结案时点口径不被覆盖；已发布报告回滚重编时撤销**有效档案**上的回写标记并写时间线；危机回溯面板与复盘状态同源于此；总览统计新增「已发布复盘报告/待审核」口径，危机卡片与总览速览展示报告状态徽标，复盘页签显示管理员待审核角标
- **权限模型**（演示，与其他模块一致）：`viewer` 只读；`ops` 值班员可建档/分段编制/刷新快照/提交审核；`admin` 管理员同 ops 且独占**审核通过、驳回、版本回滚**；越权返回 403，越态操作（审核中编辑等）返回 400。全程操作落 `crisis_report_logs`（编制/送审/通过/驳回/回滚/刷新，含操作人与职能角色），关键动作（建档/送审/发布/驳回/回滚）写入危机统一时间线
- 主要接口：`GET /api/reports`（状态过滤 + 汇总 + 字典）、`POST /api/reports`、`GET /api/reports/:id`（含快照/版本/留痕）、`PUT /api/reports/:id`（改标题）、`PUT /api/reports/:id/sections/:section`（分段保存）、`POST /api/reports/:id/snapshot`（刷新聚合）、`POST /api/reports/:id/{submit|approve|reject|rollback}`

## 通知中心（多渠道订阅与通知编排）

- **订阅编排**：订阅按「预警规则 + 话题 + 级别」匹配预警触发，或按「危机状态流转」（监测中/处置中/已结案）匹配事件，或按「协同工单事件」（`wo_event`：拆分分派 created / 超时升级 escalated）匹配工单，或按「传播路径事件」（`prop_event`：爆发升级 outbreak / 异动激增·KOL 加入 surge）匹配传播路径，或按「外部协作门户事件」（`ext_event`：提交到达 submitted / 紧急升级 escalated）匹配外部提交，或按「危机声明渠道事件」（`stmt_event`：单渠道失败 chfail / 部分渠道失败 partial）匹配声明发布；一条订阅可并发出推到多个渠道（Webhook/邮件/短信/站内信）
- **通知任务**：命中订阅即按「来源事件 × 订阅 × 渠道」生成任务（**幂等键去重**，重复触发/重启补生成均不产生重复任务）；任务状态机：待发送 → 已发送 →（需回执）已回执 / 已升级；失败退避自动重试（15s×次数），达上限置「发送失败」可手动重试；待发送/失败任务可**暂停/恢复/取消**（状态守卫，暂停期间调度器跳过）
- **调度器**：每 3 秒扫描一轮——到期任务发送/重试 + 需回执任务超时（订阅可配，分钟级）未确认**自动升级**：向升级渠道生成【升级】任务（升级链不二次升级），并写入危机时间线「通知升级」
- **回执闭环**：确认回执（幂等，重复回执忽略）→ 同步解除关联预警触发记录（`resolve_kind=notify`，状态守卫防并发重复解除）+ 写入危机时间线「通知回执」；已结案事件不回写，保证结案档案稳定
- **权限模型**（演示）：请求头 `x-user`（URL 编码）/ `x-role` 携带身份，服务端强制校验——`admin` 管理员（渠道/订阅配置 + 任务操作）、`ops` 值班员（暂停/恢复/重试/回执/取消）、`viewer` 观察员（只读，缺省）；前端右上角可切换身份，越权操作返回 403
- **历史追踪**：任务全生命周期（生成/发送/重试/失败/暂停/恢复/回执/升级/取消）落库 `notify_logs`，含操作人与时间；支持全局流与单任务日志
- **危机删除级联**：删除危机事件时（整条删除链路事务化），工单链路、危机状态类与危机声明渠道类通知任务随事件一并删除（含升级链子任务与留痕，调度器不再发送、统计同步扣减）；预警/传播/外部协作类任务的来源对象（触发记录/路径/外部提交）保留，任务仅解除危机引用——通知中心不留幽灵任务；启动时自动清理历史遗留的孤儿任务（同口径，幂等）
- 主要接口：`GET /api/notify/overview`、`POST/PUT/DELETE /api/notify/channels[/:id]`（+toggle）、`POST/PUT/DELETE /api/notify/subs[/:id]`（+toggle）、`GET /api/notify/tasks[/:id]`、`POST /api/notify/tasks/:id/{pause|resume|retry|cancel|ack}`、`GET /api/notify/logs`
- 演练约定：渠道地址含 `flaky` 首次发送模拟瞬时故障（验证自动重试）、含 `always-fail` 持续失败（验证达上限 → 手动重试）；预置「红色预警全员通知」（需回执，1 分钟超时升级）、「食安话题跟踪推送」（经 flaky 短信通道）、「危机结案通报」、「工单超时升级督办」（工单两级升级，需回执）、「协同工单分派通知」、「传播爆发升级全员通知」（传播进入爆发期，需回执）、「传播异动（激增/KOL）提醒」、「外部协作提交提醒」（品牌/监管/媒体提交到达）、「外部协作紧急升级督办」（紧急提交，需回执）、「声明渠道发布失败提醒」（单渠道失败即时提醒）、「声明部分渠道失败督办」（部分失败阻塞结案，升级专线需回执，1 分钟超时升级）十一条订阅

## 预警 → 危机闭环

- **话题 + 时间窗口归并**：每条规则可配置「归并话题」（留空则取命中舆情自身话题）与「时间窗口」（分钟，0=不限）。红/橙级预警触发时，命中**同话题且在窗口内**的未结案事件则并入，否则自动建档
- **同规则分别处置**：同一规则下，不同话题、或同一话题但已超出时间窗口的触发，分别创建独立危机事件
- **多规则并发承接**：一个危机事件可同时承接多条规则（多对多）；一条舆情同时命中多条规则时，先建档、其余规则并发并入同一事件并标记来源规则，时间线记录「规则归并」；**更高级别规则并入时事件级别自动上调**（红>橙>黄，只升不降）
- **时间窗口变更**：规则可编辑，归并话题/时间窗口变更**即时作用于后续触发**（历史归并保持不变），并写入关联未结案事件的统一时间线「规则变更」
- **解除幂等**：单条/批量解除均为幂等操作（状态守卫 `WHERE status='open'`），重复解除不重复写时间线、不产生重复计数；每条触发记录标记解除途径（`resolve_kind`：手动/批量/结案联动/通知回执/工单联动/外部协作采纳）
- **状态同步**：预警解除 → 危机时间线同步记录（标注来源规则）；危机结案 → 级联解除关联的全部未解除预警（可能横跨多条规则）
- **统一结案守卫**（`closures.js`，结案接口、回溯面板、复盘快照同一口径）：结案前四项硬阻断必须全部清零——①未完结协同工单（todo/doing/blocked）②未完结危机声明（draft/review/approved/publishing/partial）③待审核外部协作提交（pending/reviewing）④复盘报告未审核发布；未解除预警与在途通知**不阻断**——前者随结案**级联解除**、后者随结案**联动中止**（待发送不再发、待回执不再催办/超时升级，任务与留痕保留可审计，工单日志同步镜像），两类级联项在回溯面板「结案守卫检查」清单中明示
- **结案回滚**：结案事务化写入**结案档案**（统一守卫快照 `guard_snapshot` + 联动解除清单 + **通知任务中止清单与状态快照** `cancelled_tasks` + 已发布报告版本 + 结案前状态）；回滚时精确恢复被解除预警为未解除、被中止通知任务按快照恢复原状态（待回执任务重新武装回执超时倒计时，已被其他链路处理/删除的任务幂等跳过），事件重回结案前状态，全程记录统一时间线；可反复结案/回滚
- **历史档案兼容**：升级前的结案档案无守卫快照/中止清单（列为空），回溯面板按可用字段降级展示，回滚仅恢复事件状态与解除清单中的预警，不报错；调度器对已结案事件遗留的待回执任务做兜底中止（不生成升级任务），保证结案档案稳定
- **统一口径**：事件时间线（建档/归并/规则变更/解除/结案/回滚）、未解除计数（服务端 SQL 聚合，不受列表 60 条窗口限制）、总览统计（未解除预警/在办危机）三处同源
- **回溯结案**：危机事件支持回溯（按规则拆分的触发统计、关联舆情、结案/回滚档案含守卫快照与联动计数、统一守卫检查清单、完整时间线），结案时写入回溯总结完成闭环

## 批量导入（可恢复任务）

- `POST /api/imports`：`{ idem_key?, items: [{ title, content, source_id, topic, media, idem_key? }] }`，单任务上限 **5000 条**；返回 `202 + jobId`，任务异步分块执行（每块 25 条独立事务，块间让出事件循环）
- **双层幂等**：
  - 任务键 `idem_key`：同一批数据重复提交（网络抖动/双击/刷新）直接返回原任务，不重复执行
  - 条目键（`posts.idem_key` 唯一索引）：自动为 `任务键:序号`；也支持条目自带 `idem_key` 做跨批次内容去重。重试/续跑/重复提交命中已有舆情时跳过，**绝不重复触发预警、重复建档/归并危机**
- **失败重试**：单条失败用 `SAVEPOINT` 只回滚该条，自动重试至多 3 次；仍失败标记 `failed`，任务以 `failed`（部分失败）结束，可一键重试失败条目续跑；瞬时故障不影响同块其他条目
- **进度记录**：任务与逐条状态（pending/success/failed/duplicate、attempts、结果 JSON、错误）实时落库；`GET /api/imports/:id` 回写进度、预警/危机汇总与逐条结果；支持暂停 / 续跑
- **崩溃恢复**：服务重启时把 running/pending 任务转为「已暂停」并保留已提交块的进度，一键续跑断点恢复（不丢、不重）
- **闭环衔接**：每条仍走统一管线（情感分析 → 落库 → 预警触发 → 红/橙级危机自动建档或同话题窗口归并），分块提交让大批量导入时预警/危机边导入边闭环
- 其他接口：`GET /api/imports`（最近任务）、`POST /api/imports/:id/pause`、`POST /api/imports/:id/resume`（兼作失败重试）
- 演练用请求头：`x-sim-fail: 2,5`（指定条目首轮瞬时失败，验证自动重试）、`x-sim-fail-always: 5`（持续失败，验证 failed → 手动重试）、续跑时带 `x-clear-injection: 1`
- `POST /api/posts/batch`（旧接口，≤200 条）保持同步语义，内部改为创建任务并等待结束，响应结构不变（部分失败返回 207）；`POST /api/posts` 单条录入支持可选 `idem_key`，响应结构不变

## 数据源接入与采集调度

- **多源连接**（admin）：配置 API/RSS/爬虫连接的地址、入库渠道（微博/微信/新闻…）、默认话题与媒体、采集间隔、单次抓取条数与连续失败上限；连接可启停（停用同时停止其采集任务）、可编辑、可删除（采集记录保留）
- **采集任务**（ops）：值班员在任务看板一键启动/停止，启动即到期立即采一轮；运行中任务由调度器每 3 秒扫描按间隔自动采集，也可随时「立即采集」手动触发一轮
- **游标记录**：每个连接的采集游标落库（`cursor`），成功一轮随事务推进；服务重启后运行中任务按游标自动接续，不丢不重；「游标归零」可重新采集历史条目
- **失败重试**：采集失败按 15s×连续失败次数退避自动重试，达到上限任务自动停止（状态「故障停止」），修复连接后重新启动即可；每次采集（成功/失败）均落库 `collect_runs` 留痕
- **幂等去重**：条目幂等键 `collect:{源}:{外部ID}` 命中 `posts.idem_key` 唯一索引——重采、游标回退、上游分页重叠（模拟源每轮重叠 1 条）均自动跳过，**绝不重复触发预警、重复建档/归并危机**
- **闭环衔接**：每条采集舆情走统一管线（情感分析 → 落库 → 预警触发 → 红/橙级危机自动建档或同话题窗口归并 → 按订阅生成通知任务），采集记录回写当轮抓取/入库/去重/触发预警/建档危机数
- 主要接口：`GET /api/collect/overview`、`POST/PUT/DELETE /api/collect/sources[/:id]`（+toggle）、`POST /api/collect/tasks/:id/{start|stop|run|reset-cursor}`、`GET /api/collect/runs`
- 演练约定（与通知渠道一致）：连接地址含 `flaky` 首次采集模拟瞬时故障（验证自动重试恢复）、含 `always-fail` 持续失败（验证退避重试达上限自动停止）；预置「微博热搜 API」「新闻聚合 RSS」（flaky）、「论坛爬虫（故障演练）」（always-fail）三个连接
